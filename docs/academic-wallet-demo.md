## Implemented locally

A NEW Seller approval can automatically post the existing W5J-B atomic refund credit when all of these are true:

- The order belongs to an explicitly issued simulation scenario.
- The Seller is the current, active owner and the request is a new submitted Seller-review request.
- The original approved refund has its full exclusive reservation and valid source graph.
- `academic_wallet.seller_approval_credit_enabled`, `simulation_settlement.enabled`, `suki_wallet.enabled` and `suki_wallet.refund_credit_enabled` are explicitly enabled in the isolated process.

The new demo setting defaults to false. Existing production gate files remain unchanged. The new hook calls the existing credit service using the scenario's recorded, revalidated issuance authority; it does not accept an amount, destination or arbitrary funding reference. The Seller remains recorded as the actual decision actor.

Approval/Seller adjustment, reservation and credit share one outer database transaction. Both existing coordinator operations retain their own validations and mutex close checks; the outer transaction retains the mutex lock through commit. A credit failure rolls the whole new approval back. Repeated approvals cannot post a second credit or backfill an approval created before the demo switch was enabled. Partial funding preserves the approved obligation and displays **Approved — Awaiting Funding**. Historical refunds remain excluded.

The wallet shows the posted credit and verified funding status. Its Available to Spend card shows zero while checkout is unavailable. Checkout displays a disabled Suki Wallet choice, and direct calls to CheckoutService cannot create an unpaid non-COD order while payment backing is unsupported.

## Concrete blocker to the complete requested flow

The five reviewed migrations implement refund-credit backing, not a spend/reversal settlement contract. In `2026_11_15_000004_create_simulation_wallet_backings.php`, `entryCondition()` rejects a non-REFUND_CREDIT entry for a buyer with a simulation backing. Its immediate `sim_wallet_entry_*` guards therefore reject ORDER_PAYMENT and PAYMENT_REVERSAL for the very balance generated by the demo. A disposable SQLite/PostgreSQL test proves that rejection. No guard or existing test was weakened.

There are two additional connected limits: SimulationSettlementService::verify() restricts a source Seller to its single scenario order, and the existing HELD earning release requires verified completed COD purchase proof plus accepted upstream COD settlement. A wallet purchase must not manufacture COD receipts or use that release path without equivalent verified wallet settlement.

The smallest safe extension is one separately reviewed wallet-payment allocation/escrow contract and migration, then wiring it into native checkout/cancellation and earning release:

1. Allocate a payment's full server-calculated merchandise/discount/shipping total exclusively from existing immutable refund backings under the buyer lock. Conserve each backing across retained balance, payment escrow and reversals; prevent double use and overspending.
2. Link exactly one ORDER_PAYMENT to its order and exactly one PAYMENT_REVERSAL to its original debit, with immutable provenance and unique replay identities. Permit these entries only when their allocations reconcile, preserving all refund-credit graph checks.
3. Atomically create the native order, SellerOrders, inventory/voucher changes and payment records, with zero COD collection/remittance. Cancellation must reverse only eligible cancelled amounts, including correct multi-Seller/shipping allocation, once.
4. Record wallet-funded Seller earnings as HELD and release once only against verified completed wallet settlement, unresolved-return/complaint checks, existing payout reservations and deficits. Preserve the original scenario's exclusive source accounting domain or explicitly review its expansion; another scenario order cannot be silently added to that source Seller.

Simply enabling the checkout flag, writing a debit, removing a trigger, adding a payment label or setting an order PAID is not sufficient. No fake balances, new public top-up, unsupported wallet order, automatic historical refund or historical earning release was added. The requested end-to-end spend → new wallet-paid order → HELD → AVAILABLE scenario is **not implemented or claimed to pass**. Existing native earning/settlement regression tests pass independently.
