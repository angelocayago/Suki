# S-PROD-01C implementation report

Implemented locally on `seller-registration`. Existing uncommitted S-PROD-01A/01B/UX work was retained. No staging, commits, pushes, branch switches, merges, database resets, development fixtures, or production-data migrations were performed.

1. **Existing architecture.** Seller routes are closures in `routes/web.php`. ProductController delegates persistence to SellerProducts and SellerProductVariants. Products own default/simple or option-bearing variants, images and a category. `SellerAccount::current()` resolves the authenticated owner's approved shop, with the existing local-only pending-shop exception. Before this task, catalogue views filtered rendered rows with JavaScript; Reports used session arrays and a fixed seven-day chart.

2. **Stock source of truth.** `product_variants.stock`; products have no authoritative parent stock column. Listing metadata is presentation/configuration data. Database variants are queried directly; session stock is never imported. Soft-deleted variants remain excluded through the existing model scope.

3. **Threshold before and after.** Previously, Add Product/controller defaulted to 5, Products/Inventory used a fallback of 10, and Dashboard used 5 including zero. `config/seller_inventory.php` now centrally defines default 10 and business timezone Asia/Manila. SellerStock supplies PHP classification and database filtering rules. The redesigned Add Product layout is retained; only its default threshold expression changed.

4. **Zero stock.** Aggregate zero is exclusively Out of Stock and never Low Stock. A zero-stock variant has the same exclusive status. Negative adjustments and unsigned-integer overflow are rejected, rather than silently changing other stock.

5. **Exactly 10.** Low Stock under the default threshold of 10, inclusive.

6. **Exactly 11.** In Stock under the default threshold of 10. Tests also cover 1, 9 and 20.

7. **Custom thresholds.** Existing `seller_listing_data.low_stock_threshold` overrides are preserved. Missing/null thresholds use 10; new omitted/blank thresholds save 10. An explicit threshold of 5 still makes 6 In Stock; an explicit threshold of 0 disables positive low-stock classification. Thus this is a global default with optional saved product overrides, not a destructive universal replacement of historical settings.

8. **Simple-product synchronization.** The existing default variant is updated in place. Inventory adjustments lock the product and variants, change the sole quantity, and touch `products.updated_at`. No new default variant is created by stock adjustment. Inactive simple variants retain stored quantities/prices; Edit Product uses separate server-derived editable values so ordinary edits cannot overwrite them with zero/null sellable summaries. Stock and price filters describe active sellable variants; an entirely inactive configuration has zero sellable stock and no active price.

9. **Variant synchronization.** The existing Product edit service continues to preserve combinations, IDs, SKUs and references. Inventory now also offers per-variant +1/−1 controls through the existing increase/decrease routes, including legacy variant records. The optional integer `variant_id` must belong to the owned product. Siblings and inactive variants remain unchanged. CSRF, seller ownership, integer validation and transactional locking remain in force. No checkout/order events deduct stock in this task.

10. **Aggregation and alerts.** Product sellable quantity is the sum of active, non-deleted variants exactly once. Aggregate badges and exclusive stock filters classify this sum using the effective threshold. Separate variant details show each stored quantity, inactive exclusion and individual stock status. An aggregate above 10 can be In Stock while displaying low-stock variant alerts. All active variants at zero means Out of Stock. Dashboard reloads saved catalogue data and shows aggregate shortages or variant warnings for active listings. Its unrelated order/revenue logic was left outside this stock task.

11. **Inventory filters.** Database conditions support product-name, SKU and stored variation-label search; locked main category; supported subcategory; existing active/inactive/draft listing statuses; exclusive aggregate stock status; simple/variation type; specific owned variant; minimum/maximum sellable stock; minimum/maximum displayed price; date field and date preset. Sorts are name A–Z/Z–A, stock ascending/descending, updated descending and price ascending/descending. Variant stock controls and product edit links are retained.

12. **Products filters.** Products uses the same query/filter service and controls. Price conditions use the minimum active variant price shown by the listing, including the persisted effective sale price for simple products. Parent metadata cannot override real variant stock or prices. Existing thumbnails, product actions, responsive layouts and Edit Product links remain. Search matches any saved SKU, including a variant SKU.

13. **Reports filters.** Reports now queries persisted order items joined to orders and optional seller_orders. It supports all shared date presets, specific owned product, locked main category, supported subcategory, backed order/fulfillment statuses, actual saved payment methods and product-breakdown sorting by gross sales, units or recency. Legacy identity uses the shop owner's user ID on both order and item; normalized identity uses `seller_orders.seller_id` and verifies the matching parent order. Session order arrays cannot establish report ownership or revenue.

14. **Metric sources and limitations.** All report components derive from the same filtered saved item records:

    | Metric/component | Source and meaning |
    | --- | --- |
    | Matching orders with items | Distinct `order_items.order_id` in the qualifying dataset |
    | Completed/delivered orders | Distinct qualifying orders whose effective seller-order/order status is delivered or completed, normalized to lowercase |
    | Units sold | Saved quantities of qualifying completed/delivered items |
    | Gross completed sales | Saved item unit price × quantity; `unit_price_minor / 100` takes precedence for normalized items, otherwise legacy `unit_price` |
    | Product breakdown | The same completed items grouped by product ID or historical product slug, preserving snapshot names |
    | Daily charts | The same records grouped by order creation date in Asia/Manila; chart gross amounts and order counts match the filtered cohort |
    | Item table | The same filtered saved item records, with their effective status and gross amount |
    | Discounts/refunds/net revenue/payouts | Explicitly unavailable at this item scope; no reliable product-level allocation/refund/payout ledger was found |

    Gross completed sales excludes shipping and does not imply payment. Existing orders default to UNPAID, so order existence/delivery is not treated as paid revenue. Orders without recorded items are excluded and the UI labels this scope. No fake revenue, growth figures or sales were added. PHP formats currency to two decimal places.

15. **Combined filters and date behavior.** Applicable conditions combine with AND before selecting records. Inventory/Products date field is `products.created_at` (Date Added) or `products.updated_at` (Last Updated). Reports uses `orders.created_at`, explicitly labelled as order creation date; completed sales describe the current completion status of that creation-date cohort, not a completion-date cash-flow series. Presets: All Time, Today, Yesterday, Last 7 Days, Last 30 Days, This Week, Last Week, This Month, Last Month and Custom. Rolling presets include today plus the previous 6/29 calendar days. Weeks begin Monday. Calendar weeks/months use their full calendar boundaries. The server calculates Manila boundaries and converts them to the configured application/storage timezone (currently UTC). Bounds are start-inclusive and next-day-exclusive, covering every instant of the selected end date. Invalid dates, unsupported presets and reversed ranges return validation errors. `updated_at` is never called a restock timestamp.

16. **Pagination, sorting and UX.** Catalogue filtering runs in SQL before 15-product pagination; summary cards cover all matching records. Sort identifiers are whitelisted and product ID is the stable tie-breaker. Reports applies SQL filters before deriving metrics and paginating 20 saved items; its item table is consistently recent-first with stable original ID ordering for ties, while the labelled breakdown sort controls the product breakdown. GET query strings preserve selections across refresh and pagination. Accessible labels, selected values, Apply Filters, Reset Filters, counts, empty states and responsive green filter panels are provided. No asynchronous loading behavior is needed. No export endpoint existed to synchronize.

17. **Accuracy and isolation tests.** SellerStockFilteringTest covers all six stock boundaries, historical/custom thresholds, inactive variants, high aggregate plus low variant, all-zero active variants, no double counting, default threshold creation, inactive simple edits, transactional simple/variant updates, stable references, invalid quantities/variant IDs, search/category/status/type/price/quantity/combined filters, sorting, reset via clean GET, pagination state, every bounded date preset, All Time, inclusive endpoints, month/year transitions, Manila conversion, malformed/reversed dates, report totals/chart/table consistency, normalized order ownership and cross-seller isolation. All fixtures use `RefreshDatabase` and the configured isolated SQLite `:memory:` test database. ReportsAccuracyTest now tests persisted fixtures and rejects session-only ownership. RolePortalRouteAccessTest retains the existing session gate and verifies persisted seller identity for the refreshed dashboard catalogue.

24. **Orders/Earnings & Payouts audit.** `/seller/orders` and `/seller/sales` still consume `session('orders')`. The sidebar's Earnings & Payouts destination is this Sales page, not a persisted payout ledger. Sales currently reads `total`/`grand_total` session values and does not prove payment. A follow-up should first scope saved legacy orders/items by owner and normalized seller_orders by shop, then reuse SellerDateFilter before pagination/metrics. Trustworthy stored candidates: orders.created_at, nullable placed_at, delivered_at and completed_at; lifecycle timestamps such as confirmed_at, preparing_at, ready_for_pickup_at and cancellation/return timestamps where populated. Normalized seller_orders has created_at, updated_at and nullable delivered_at, but no dedicated completed_at. `updated_at` must not stand in for payment or payout date. Payment has a model but this migration set provides no trustworthy payment/payout settlement history. Do not expose paid-at/processed-at/payout-date filters until persisted records and ownership paths exist. No order/payment/fulfillment workflow was changed here.
