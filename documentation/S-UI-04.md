# S-UI-04 implementation report

Implemented locally on `seller-registration`. Existing uncommitted work was retained. No staging, commits, pushes, branch changes, destructive commands, development fixtures or database migrations were performed.

1. **Pages audited.** Products, Inventory, Reports, Sales, Orders, Promotions, Dashboard and account/settings destinations. Products/Inventory already used SellerCatalogueFilter. Reports used persisted order items. Sales and Orders read session arrays. Promotions also uses session records; profile/settings pages have no meaningful listing dataset. The implementation plan was to extract Products' filter presentation, reuse it for Inventory/Reports, integrate persisted Sales through a shared seller-owned item query, and defer workflow-dependent Orders/Promotions integration.

2. **Pages implemented.** Products now uses the extracted shared presentation while retaining its selection/table behavior. Inventory and Reports gain collapsible filters, counts and removable chips without losing fields or actions. Sales gains the same interface and an actual persisted, database-paginated dataset. No superficial session-only filter panel was added to Orders or Promotions. Static settings and profile pages were left alone.

3. **Shared Blade partials.** `seller.partials.filter-trigger`, `advanced-filter-panel` and `active-filter-chips` provide the trigger/count, panel/close/no-JavaScript fallback and chip links. Existing `data-filters` continues to render catalogue/report fields. New `sales-filters` renders transaction fields. Each page supplies its own unique panel ID, choices, chips and dataset. The SUKI SHOP green styling, headings, cards, shell and responsive layouts are retained.

4. **Shared JavaScript.** `resources/js/seller-filters.js` owns opening/closing, aria-expanded, Escape and focus restoration, with a per-root initialization guard. It loads through the existing app → product-listing import chain. `seller-product-listing.js` delegates filter behavior to it and retains only its own current-page product-selection behavior. No separate page-specific filter scripts, AJAX, client-side data filtering or JavaScript date calculations were added. Scoped filter CSS now targets `data-seller-filters` on all four pages.

5. **Products compatibility.** Existing filters, grouped chips, default-count rules, query navigation, seller constraints, thumbnails, stock/listing badges, Edit Product links, current-page selection, Select All/indeterminate state, Clear Selection and history-reset behavior remain. The existing Products feature and JavaScript regression tests pass. Its `SellerProductFilterChips` entry point remains as a compatibility wrapper around the generic formatter.

6. **Inventory.** The Stock Levels header now has Filters beside Product Management. All existing name/SKU/variation search, status, stock status, type, specific variant, sort, category, subcategory, date field/range, custom dates, stock bounds and price bounds remain. The default expanded grid is replaced with the shared panel. Summary cards still describe all matching records, not just the current page. Stock 0/10/11 classification, custom overrides, inactive-variant exclusion, per-variant alerts, thumbnails, quantity controls and Edit Product are unchanged. Filtering never adjusts stock.

7. **Reports.** The Reports & Analytics heading gains Filters. Product/category/subcategory/status/saved payment method/date/breakdown-sort fields remain. The panel opens when criteria or validation errors are present. Chips and removal links apply to the same persisted query that drives cards, daily charts, product breakdown and item table. The date field remains order creation date, and gross completed sales remain distinct from payment receipt. Existing empty states remain honest.

8. **Sales source discovered.** The previous Sales route passed `session('orders')`; its Blade calculated amounts from `total`/`grand_total`, independently of database ownership, with no settlement evidence. Both legacy user-keyed orders/items and normalized shop-keyed seller_orders exist. The `payments` table/model also exists with order_id, method, amount_minor, status, provider_ref and timestamps. No seller payout/settlement allocation ledger or verified payment-lifecycle integration was found in the inspected application paths. Correction to the earlier S-PROD-01C audit: a payments migration does exist; the missing capability is trustworthy seller settlement attribution and payout history.

9. **Sales data integration.** New `SellerOrderItems` supplies the shared persisted source for Sales and Reports. Normalized items must reference the authenticated shop's seller_order and matching parent order. Legacy items require the authenticated shop owner's user ID on both order and item. Once an order has normalized seller-order records, unlinked legacy copies are excluded, avoiding duplicate sales during schema coexistence. No session financial totals or client-supplied seller IDs establish ownership. Historical snapshots remain usable without requiring a currently active product.

10. **Sales fields.** Product, assigned main category, supported subcategory, actual supported order status, saved payment method, all ten existing date presets, custom From/To and sort. Sorts: Newest First, Oldest First, Highest Transaction Amount and Lowest Transaction Amount. Product selection is seller-scoped and uses saved product IDs with the existing legacy-slug fallback. Method choices come only from owned persisted item/order records. No payment-status or payout-status selector was added because an order-wide method/status or unallocated payment attempt does not establish seller settlement.

11. **Sales cards and table.** All four cards describe the complete filtered item cohort across pages:

    | Card | Definition |
    | --- | --- |
    | Gross Completed Sales | Sum of matching saved item unit price × quantity for effective delivered/completed statuses |
    | Pending Item Value | Matching item values for supported non-final fulfillment statuses, excluding completed/delivered/cancelled/returned/delivery_failed; unknown statuses are not assumed pending |
    | Average Completed Order Value | Matching gross completed item value divided by the count of matching completed orders; Unavailable when no qualifying order exists |
    | Cancelled / Failed | Count of matching cancelled, returned or delivery_failed order transactions |

    Normalized `unit_price_minor / 100` takes precedence; legacy `unit_price` is the fallback. Shipping and unallocated discounts are excluded. Refunds are not invented. Product/category filters restrict transaction amounts to the matching items, rather than retaining an unrelated full-order total. Recent Transactions shows saved reference, order creation date in PHT, units, effective status, recorded method and gross item value. Orders without seller-owned recorded items are excluded and labelled accordingly. Sorting and 20-transaction pagination run in SQL, with stable order-ID/status tie-breakers; Sales does not load every order into PHP.

12. **Unavailable financial metrics and naming.** Verified received earnings, seller-settled payments, refunds, net revenue and payouts are explicitly unavailable. Neither COD choice nor delivered/completed status is treated as confirmation of payment. Payment attempts are not joined into item aggregation, preventing amount multiplication or false payment attribution. The sidebar destination is now accurately labelled **Sales**, with its existing icon, location and `seller.sales` link retained; its title states that payouts are unavailable. No fake payouts page or settlement calculations were created.

13. **Orders and other dependencies.** Orders remains unchanged. Its session-based view includes transitions posted to `order.status.update`, whose route is admin-gated, and expects legacy detail/timeline/amount arrays. Replacing its dataset alone could leave incorrect or unauthorized workflow controls. A separate task must define seller-specific order authorization, persisted detail mapping and permitted actions while preserving checkout/fulfillment. Current Orders session ownership/filtering remains an unresolved dependency, not a claimed security fix in this task. Promotions likewise needs persisted seller ownership/integration before standardizing its filters. Dashboard short summaries and static account pages were not given unnecessary filter panels.

14. **Chips and reset.** Generic `SellerFilterChips` builds escaped labels from page-specific options and known parameters. Count equals meaningful rendered criteria. All/empty values, page, unsupported parameters and each page's default sort are excluded. Custom date bounds, stock bounds and price bounds are grouped. Default Date Added is not counted; Last Updated counts only with an applied catalogue date range. Removal links preserve other whitelisted criteria and drop pagination; removing a date chip also removes its From/To. Reset links use each page's clean GET route. Query values remain populated on reload. Panels preserve draft input when closed, reopen for applied filters/errors, and have a working no-JavaScript form fallback.

15. **Date semantics.** Existing SellerDateFilter is unchanged. Asia/Manila business dates are converted to configured application/storage timezone boundaries (UTC in this project). The start is inclusive, the next midnight after the selected end date is exclusive. Rolling 7/30-day presets include today plus the prior 6/29 calendar days; weeks start Monday; calendar month/week presets use calendar boundaries. Invalid/malformed/reversed dates return validation errors. Inventory uses Date Added or Last Updated; Reports/Sales use saved order creation date. No restock, payment-received or payout dates are invented.

16. **Isolation, safety and performance.** SellerAccount still resolves an active authenticated seller and the approved shop, with the existing local-only pending-shop exception. Catalogue ownership, product/variant validation, categories and stock transactions are retained. The shared item query prevents foreign shop/order/item selection and mismatched normalized parent references. Sort identifiers are fixed and whitelisted; raw status/amount SQL consists only of trusted constants. Sales summaries and grouped pagination run in the database with a constant number of queries, not per-row lookups. Reports retains its existing filtered-item materialization for charts/breakdowns; this task does not expand it to unfiltered orders. A future grouped-SQL Reports optimization can address very large filtered cohorts. No real data was changed by UI verification.
