# S-BUYER-DEV-01 local Buyer access report

Implemented the explicitly authorized local OTP/email and Buyer approval eligibility exceptions. Existing Buyer records are not approved or verified in storage. No migrations, development fixtures, password changes, OTP deletions, staging, commits, pushes or branch changes were performed. Existing Seller and messaging work was retained.

1. **Actual blockers.** Buyer registration is a closure in routes/web.php, not a separate registration controller. It normally creates a Buyer with status=pending and email_verified_at=null, saves the address and identity-document upload, issues an email OTP and redirects to verification. BuyerEmailVerificationController and BuyerEmailVerificationService verify the code and set the email timestamp; verification alone leaves status pending. Admin approval requires verified email and separately activates the account. Login first checks credentials/suspension, then the OTP gate and active status. The shared $requireBuyer closure implements the Buyer portal gate; no dedicated Buyer verification middleware is registered. SellerMessaging separately required active status and verified email. The initial OTP-only request could not satisfy immediate registration access; implementation followed the user's explicit subsequent authorization to add a local approval exception too.

2. **Central rule.** New app/Support/BuyerAccess.php evaluates the actual application environment, persisted Buyer role, status and suspension. Only APP_ENV=local permits an otherwise eligible Buyer with pending/active status to satisfy approval/email eligibility without changing stored fields. Accounts with Seller, Admin, SuperAdmin, Rider or Logistics roles cannot use this exception. Rejected/inactive/unknown statuses and suspended accounts remain excluded. Request fields, cookies and session flags cannot enable it. No configuration flag defaults production into bypass mode.

3. **Local registration and login.** Registration validation, ownership, role assignment, address and file persistence remain unchanged. After successful normal creation, an eligible local Buyer is redirected to login without sending an OTP. The success message identifies local access and unchanged saved approval/verification state. Registration does not automatically authenticate the account. The Buyer can then log in with their genuine password and access Buyer pages and Messages immediately. Credentials, session regeneration and role checks remain. The shared Buyer gate also explicitly rejects suspended accounts. No checkout/cart/order-processing handler or monetary logic was edited.

4. **Stored state and scope.** New local Buyers remain pending and unverified. Existing accounts, passwords and OTP rows are not rewritten. This code-only local eligibility rule also accepts otherwise eligible existing pending Buyer accounts when they log in locally; it does not bulk approve them or create approval evidence. No per-account/session bypass marker is introduced. Active unverified local Buyers also qualify. Switching to a non-local environment immediately restores the existing stored-state restrictions, including for an already authenticated account when the relevant portal/messaging gate runs. A locally created account still needs genuine verification and approval for non-local use.

5. **Production and approval protection.** Non-local environments preserve the existing OTP-backed login/portal guard, active-status requirement, actual OTP verification routes/service/controller and Admin approval handler. Messaging continues to require verified email and active Buyer status outside local. Existing legacy Buyer portal behavior, where the OTP redirect is tied to an existing OTP row, is not broadened or replaced by this task. No fake verification/approval event is emitted. SellerAccount and Seller approval rules are unchanged; the pre-existing separate local pending-shop administration convention is not modified.

6. **Messaging and private images.** SellerMessaging::eligibleBuyer delegates only approval/email eligibility to BuyerAccess and retains actual Buyer identity and suspension checks. Its existing calls cover initiation, send, owned Buyer history, participant revalidation for replies, and ChatImageController's Buyer authorization. No ownership, message history, file validation/storage, unread counts, read receipts or Seller reply code was changed. Tests prove local pending/unverified Buyer image upload and authorized image retrieval, continued sends, foreign-thread/image rejection, Buyer exclusion from Seller/Admin destinations, and rejection after switching to production. The existing OTP row remains byte-for-byte equal in those fixtures.

7. **Exact files changed.** Added app/Support/BuyerAccess.php (central local eligibility rule), tests/Feature/BuyerLocalAccessTest.php (isolated regression cases) and this report. Modified routes/web.php only at the two Buyer OTP gates, Buyer portal account gate, login status gate and post-registration local redirect; modified app/Support/SellerMessaging.php only at eligibleBuyer(). OTP controllers/services/models/schema, User/Seller models, SellerAccount, routes/route names, registration approval writers and other business modules were not edited. No route was added or removed. No existing file was deleted.

8. **Focused tests.** New BuyerLocalAccessTest: **12 passed, 120 assertions**. Combined new local access + existing BuyerRegistrationValidationTest, BuyerSellerMessagingIntegrationTest, SellerMessagingTest and RolePortalRouteAccessTest: **105 passed, 981 assertions**. Coverage includes actual local HTTP registration/login without OTP or status/timestamp mutation; private images and messaging; preserved OTP data; production/staging/testing verification and approval requirements; verified active non-local access; client bypass-field rejection; suspended/rejected/inactive and wrong-role rejection. Existing OTP issue/verify/resend/expiry and Admin approval tests remain intact. The initial new test run revealed only fixture issues: a data-provider argument nesting error and attribute array ordering in the preservation assertion; both were corrected before passing runs.

9. **Isolation and quality.** Tests use testing environment, SQLite :memory:, empty DB_URL and array sessions/cache; environment-specific cases switch the application environment against that same isolated database. Valid CSRF tokens are supplied in local/production HTTP cases. Image tests enable GD only for their process; the final Artisan suite uses a temporary INI directory that is removed afterward, without changing global PHP configuration. PHP syntax checks passed for all four changed/new PHP files. Targeted Pint passed for the helper, messaging service and new test; routes were not broadly formatted. All **37 JavaScript tests**, Blade compilation, Vite build and git diff --check passed. No frontend implementation was changed.

10. **Remaining limits.** The exception exists only while the actual app environment is local; it should be removed when local testing is complete. It does not deploy the S-MSG-02 image table, enable GD globally or raise web-server upload limits. Those existing image prerequisites still need separately managed deployment/configuration. No manual browser walkthrough was performed for this backend access change. Real email verification and Admin approval remain required when leaving local. Stopped Buyer checkout integration and Seller order transitions remain untouched.

11. **Final full suite.** `php artisan test --compact`: **544 passed, 5,155 assertions**, 55.22 seconds. Existing Seller Products, Inventory, Orders/Details, Sales/Reports, profiles, vouchers, notifications, messaging/images, Buyer checkout and role-access regressions passed. The CLI application environment was independently confirmed as local and cached configuration was absent. No environment file or global PHP configuration was changed. All implementation/report changes remain local and unstaged.
