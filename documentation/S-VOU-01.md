# S-VOU-01 implementation report

Implemented locally on `seller-registration`. The four existing tracked S-ORD-02 changes and 36 pre-existing untracked entries were retained. No fetch, pull, merge, branch switch, staging, commit or push was performed. No development/production migration or commerce data write was performed. Stopped Buyer integration and Seller status mutations remain deferred.

1. **Current SUKI audit.** There was no persisted voucher model/table or seller voucher controller. Existing Promotions is a session-backed collection of campaign/direct-discount configuration, with percentage/fixed values, dates, product association and status. Its existing GET/POST/DELETE behavior remains intact. Product sale metadata uses `seller_listing_data` (regular/sale price and on-sale flag); active variant prices supply the effective saved prices. No authoritative stacking or voucher allocation contract was found. Existing Order voucher fields do not establish a working redemption system. Sales/Reports and their gross expressions were inspected and left unchanged.

2. **KILA reference actually inspected.** No KILA ARINGO source was located in the checked repository, local project roots or known user Desktop/Documents/Downloads locations. One user-directory inventory was inaccessible. No KILA controller, model, calculation service, redemption integration, view or test is claimed as inspected. The supplied feature inventory was the behavioral reference. KILA-specific rounding, code scope, historical versioning and checkout behavior could not be verified; the explicit SUKI policies below were chosen instead.

3. **Capabilities.** Persistent creation, viewing, permitted editing, percentage/fixed discounts, minimum eligible subtotal, percentage cap, Manila scheduling, optional total limit, required per-buyer limit, all/selected seller products, activation, pause, computed availability and archive are implemented. Codes remain immutable after creation, even before usage. There is no permanent-delete endpoint. Used terms lock rather than being silently rewritten; name and description remain editable, and withdrawal remains possible.

4. **Database and migration strategy.** Added `database/migrations/2026_10_23_020000_create_seller_vouchers.php`. `seller_vouchers` holds shop ownership, code/name/description, type, percentage basis points or fixed centavos, minimum/cap centavos, product scope, schedule, limits, recorded usage counter, terms lock, active/paused configuration, archive and timestamps. `seller_voucher_products` stores unique voucher/product pairs. Foreign keys restrict deletion of referenced shops/products/vouchers. No historical schema, Orders or checkout totals were modified. There is no speculative redemption table. The migration must be applied through the project's normal reviewed deployment process before these pages can query a development/deployment database; it was not applied there during this task. Isolated tests exercised migration creation on SQLite only.

5. **Routes and authorization.** Nine controller routes were added under `seller/vouchers`, names prefixed `seller.vouchers.`. All use `web` and `auth`, then `SellerAccount::current()` on each action. Persisted seller role, active/non-suspended owner, exactly one eligible shop, approval and the local-only pending exception are reused. Foreign voucher lookup is seller-scoped and returns 404. Request `seller_id` never establishes ownership. Mutations use CSRF-protected POST/PUT forms, server validation and transactions; edits/lifecycle actions lock the voucher row.

6. **Validation.** Names are required (100 characters); descriptions are optional (2,000). Percentage values allow 0.01–100.00 with at most two decimal places. Fixed values must be positive, up to PHP 42,949,672.95. Minimum spend is optional/nonnegative; percentage caps are optional/positive and prohibited for fixed discounts. Scientific notation, negative values and excess precision are rejected. Limits are positive integers up to one billion; per-buyer cannot exceed a configured total. Selected scope requires distinct owned product IDs (maximum 500). Dates require exact datetime-local minute precision, and end must follow start. An expired paused configuration may be retained for historical administration but cannot be activated. Client-supplied counters/lock/archive fields are not writable through the forms.

7. **Code policy and concurrency.** Codes are ASCII uppercase, trimmed, 3–32 characters, starting with a letter/digit and continuing with letters, digits, underscore or hyphen. Internal whitespace and unsupported characters are rejected. Codes are globally reserved across shops and archived records. The unique database index is case insensitive through SQLite NOCASE or MySQL/MariaDB utf8mb4_unicode_ci; PostgreSQL additionally gets an UPPER(code) unique index. Server uniqueness validation provides normal errors, while database unique-constraint exceptions are converted to code validation errors if concurrent requests collide. A two-process SQLite test uses the actual migration-generated table/index DDL: one case-only competing insert succeeds, the other receives a uniqueness collision. This does not establish MySQL/PostgreSQL execution verification.

8. **Money and preview.** Financial configuration uses integer centavos, percentages integer basis points. Decimal strings are converted without floating-point arithmetic. Percentage estimates round half up to the nearest centavo; fixed/percentage discounts never exceed the supplied eligible subtotal, apply the minimum first, and respect a percentage cap. The details-page GET preview accepts an example eligible seller-product subtotal and computes on the server. It is clearly illustrative and independent of voucher availability; it does not validate a real cart, reserve usage or apply a discount to an Order. PHP 500 at 10.25% estimates PHP 51.25 before any cap.

9. **Eligibility.** Products belong to `sellers.id`. New selections must be active, non-deleted seller-owned products with at least one active non-deleted variant. Foreign/nonexistent/inactive/deleted new attachments are rejected. Previously selected own inactive/deleted products may remain linked and are displayed as unavailable, preserving configuration history. They do not qualify for activation. All-products scope is dynamic and can include future eligible seller products. This is product-level restriction; no variant/SKU restriction is claimed. Saving voucher configuration never changes a product, price, SKU, variant or stock quantity.

10. **Lifecycle and history.** Active/paused is saved configuration. Activation rejects expired, exhausted, malformed financial/limit terms or a scope with no eligible products; a failed save rolls back both voucher and pivot changes. Pause withdraws availability. Archive records a timestamp, pauses the offer, preserves counters/products/code and is idempotent. Archived records are viewable and cannot be edited/reactivated. If `used_count > 0` or `terms_locked_at` is set, material term/status inputs are rejected by the edit action; only name/description are updated. Separate Pause/Archive actions remain available. S-VOU-02 must set the lock/counter atomically when real redemption is introduced.

11. **Expiration and scheduling.** Seller input/display uses Asia/Manila. Saved timestamps are converted to the configured application/storage timezone (UTC here). The start boundary is inclusive and end exclusive. SQL computes availability without changing rows: archived, paused, expired, exhausted, unavailable products/shop, scheduled, active. Active configuration cannot override expiry or missing eligible products/shop approval. Local pending shops can administer configuration under the established exception but are labelled unavailable until approved. No cron job or fabricated redemption state is needed for expiration.

12. **Usage boundary.** New counters are genuinely zero. No action in this module increments usage, records a purchase/redemption, joins payment attempts or promises Buyer redemption. Saved limits are configuration only; per-buyer enforcement is deliberately absent until a buyer/redemption ledger exists. The terms lock and aggregate counter are foundations, not a substitute for that ledger. Tests that set counters explicitly do so solely in isolated fixtures to verify lock/exhaustion behavior.

13. **Filtering and pagination.** The existing shared trigger, advanced panel, chips and JavaScript are reused. Server search covers name/code; controls cover computed availability, type, all/selected scope, eligible product, creation-date presets/custom range and stable newest/oldest/ending/name sorting. Seller ownership precedes filters. SQL pagination is 15 vouchers; matching counts use paginator totals. The existing Manila date helper supplies calendar boundaries. Default sort/empty values/page are excluded from chip counts; custom bounds form one removable date chip. Chip removal drops pagination and preserves other allowlisted criteria. Reset points to the clean voucher index. No AJAX/client-only filtering or new production JavaScript was added.
