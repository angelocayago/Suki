# S-ORD-02 implementation report

Implemented locally on `seller-registration`, extending committed S-ORD-01. Initial working tree had no tracked changes and 31 pre-existing untracked entries. Those entries were retained. Stopped Buyer integration work was not resumed. No staging, commits, pushes, merges, fetches or branch changes were performed.

1. **Task summary.** Added a dedicated, authenticated, read-only Seller Order Details page. The existing persisted listing, filters, pagination, summaries, badges and native Preview remain intact. Each authorized listing row now includes View Details.

2. **Files.** Modified `app/Support/SellerOrders.php` (narrow details query and safe return-navigation builder), `resources/views/seller/orders.blade.php` (allowlisted listing context and View Details link), and `routes/web.php` (one new GET closure). Added `resources/views/seller/order-details.blade.php` and `tests/Feature/SellerOrderDetailsTest.php`. Updated `tests/Fixtures/seller-product-routes.json` by adding only the intentional new route contract; existing route expectations remain. Added this report and `S-ORD-02-routes-before.json` / `S-ORD-02-routes-after.json`.

3. **Contracts reused.** `SellerAccount::current()`, `SellerOrderItems::owned()`, `STATUS_SQL`, `GROSS_SQL`, `ProductImageUrl::url()`, the existing Seller shell, and existing listing/date/sort conventions. Shared ownership, Sales and Reports services were not changed. `SellerOrders::data()` remains unchanged; details retrieval is a separate narrow method in the same class.

4. **Route.** Added `GET|HEAD /seller/orders/{order}`, named `seller.orders.show`, action `Closure`, middleware `web`, numeric route constraint. The closure uses the existing seller guard, then resolves the persisted shop via `SellerAccount::current()`. It calls `SellerOrders::details()` and `backUrl()`. No mutation endpoint was added.

5. **Route inventory.** Before: 136. After: 137. All original domains, methods, URIs, names, actions and middleware match. Only the dedicated Details route was added. Source-location metadata for following closures shifts because lines were inserted; this is not a change to their route contracts. No registered duplicate names or method/URI collisions were introduced. The existing `seller.orders` route remains a GET|HEAD Closure at its original URI.

6. **Seller identity.** The authenticated User must have the Seller role, active status and no suspension, and resolve to exactly one approved shop. Pending shops retain their existing local-only exception. Guests with only the legacy Seller session flag cannot pass the details resolver. Missing eligibility returns the established 403/redirect behavior; multiple eligible shops remain 409.

7. **Normalized and legacy ownership.** The parent order ID is a lookup key, never authorization. The shared owned-item query verifies shop-owned SellerOrder plus matching parent Order. Legacy items require matching owner-user IDs on both item and parent, no SellerOrder link and no normalized groups on the parent. Null ownership, foreign sellers, inconsistent parents, empty groups and partial-normalization leftovers cannot establish access. Unavailable/foreign/no-owned-item requests return 404. No fallback to session orders or unrestricted Buyer Order exists.

8. **Details query.** A single query loads only attributable snapshots for the requested parent ID. It selects a limited set of parent metadata alongside saved item fields; no unrestricted Order model or item relationship is loaded. Identifier validation rejects noncanonical, zero and overflowing integers. The normalized unique `(order_id, seller_id)` contract and legacy precedence provide one authorized segment per shop/parent. The handler additionally rejects multiple distinct segment identities if deployed data violates this invariant. Presentation objects expose only the fields used by the page. No per-item database lookup is performed.

9. **Purchase snapshots.** Names, variants/options, quantities, unit prices and recorded line totals come from saved OrderItems. Current product records, current prices and current SKUs are not consulted. Missing, edited, inactive or soft-deleted products do not hide attributable purchases. Duplicate slugs retain distinct item IDs. There is no saved SKU column in the inspected item schema, so the page says SKU at purchase: Not recorded. Images reuse the existing products-only local public-storage resolver; missing/unsafe references receive a neutral image-unavailable placeholder. Legacy absolute storage URLs are resolved as local assets, not fetched remotely.

10. **Money.** Seller Item Gross follows the existing SQL expression exactly: saved minor-unit unit price / 100 when non-null, else saved decimal unit price, multiplied by saved quantity. Zero minor-unit price is respected. Gross sums only owned lines. If the separately recorded line_total differs, it is shown explicitly as Recorded line total; neither saved value is repaired. Parent totals, shipping, unallocated discounts, commissions and refunds are not allocated to the seller. No received-earnings, settlement or payout figure is calculated.

11. **Statuses.** Effective fulfillment uses the unchanged lowercased SellerOrder status, otherwise parent Order status. Display labels replace underscores only; they do not equate different vocabularies. The status source is labelled; normalized details show parent status separately. Unknown saved states receive neutral styling. Only the saved order creation time is displayed, in Asia/Manila with an ISO time value. No invented timeline or milestones are shown. Payment method and parent-order payment status are labelled recorded fields; they do not prove seller receipt, collection, remittance or settlement. Payments/Shipments/DeliveryEvents are not queried for fabricated evidence.

12. **Buyer privacy.** Only the saved recipient name is disclosed for order identification, consistent with the listing. Buyer account records, phone, full delivery address, instructions, identity documents, unrelated addresses, payment-provider references and other sellers' items/amounts are not selected or displayed. Contact/address disclosure remains deferred until legitimate seller fulfillment actions exist.

13. **Navigation.** Listing links carry only allowlisted existing criteria and current page in a nested `list` query. Back to Orders and the Orders breadcrumb use a locally constructed named-route URL. The handler accepts criteria rather than a return URL, validates scalar types, date bounds, sort and page, discards unsupported keys and falls back to the clean Orders URL for invalid input. External return URLs are never followed or rendered. The details lookup itself is independent of listing filters.

14. **UI.** The existing SUKI Seller layout, sidebar/topbar, fonts and green styling are reused. The new page has Dashboard / Orders / Order Details breadcrumbs; saved reference, date and status header; Back to Orders; Overview; Purchased Products; Seller Item Gross; Fulfillment Status; Payment Information; and Recipient cards. Product rows and the card grid adapt to narrow widths. No CSS or production JavaScript files were changed. Existing Preview and shared filters remain.

15. **Security tests.** Tests cover owned and foreign normalized/legacy orders, shared parents, HTML/amount isolation, owner/shop IDs differing, altered/overflowing route IDs, null owners, parent mismatches, partial normalization, normalized precedence, local-only pending access, ineligible and multiple shops, session-only guests, other roles, safe return navigation, escaping and image-path handling. Data isolation is enforced in the query, not by hiding HTML.

16. **Database.** No migrations, schema/index changes, historical repairs, backfills, development fixtures, stock changes or commerce mutations were performed. Order and OrderItem models were not edited. The four removed S-INT-01B files remain absent. Read-only GET tests snapshot existing Orders, OrderItems, SellerOrders, Products, ProductVariants, Payments, Shipments, DeliveryEvents and Sellers, including isolated nonempty payment/shipment/event/stock fixtures, and verify identical records after viewing. POST to the Details URI returns 405. The shared shell's existing logout form is unaffected.

17. **Focused PHP results.** New Details suite: **27 passed, 202 assertions**. Combined Details + S-ORD-01 listing suite: **65 passed, 438 assertions**. The first focused run exposed an overly broad test assertion that rejected the shell's legitimate script tag; it was narrowed to assert that the specific malicious saved script payloads are escaped. No application escaping defect was found. Equivalent gross values reconcile with the existing listing, Sales and Reports in isolated fixtures.

18. **Full PHP results.** **414 passed, 4,069 assertions**. This includes Seller products/variants/SKUs/images/inventory/profiles, S-ORD-01, Sales/Reports, Buyer checkout and Admin/Rider/Logistics access tests. PHPUnit isolation was checked before edits: SQLite `:memory:`, testing environment, array sessions/cache; cached config was absent. Commands explicitly set these isolation environment values. No tests ran against the configured development database.

19. **JavaScript results.** **31 passed, 0 failed**. No JavaScript changes were required; existing shared-filter, product selection, image, variant and logout behavior tests continue to pass.

20. **Other checks.** PHP syntax checks passed for SellerOrders, new test and routes. Targeted Pint passed for the service/test; unrelated routes formatting was not rewritten. `php artisan view:cache`, `npm.cmd run build` and `git diff --check` passed. The historical route fixture was extended with the single intentional GET route rather than weakening its regression assertion.

21. **Browser verification.** Not performed. Browser inventory returned no apps/browsers, and opening an in-app browser returned `Browser is not available: iab`. Automated response/DOM tests and build checks do not establish visual desktop/mobile rendering, keyboard navigation or real-browser behavior. No fake development orders were created for screenshots.

22. **Known limitations.** Checkout attribution remains unchanged: purchases lacking verified seller attribution remain unavailable. Partially normalized leftovers are conservatively excluded. Historical SKU snapshots, seller settlement evidence and a connected fulfillment timeline are absent from the supported contract. Applied deployment schema, MySQL behavior and large individual-order rendering performance were not verified. The detail page loads all owned lines of the one requested order to show a complete segment; it does not load unrelated orders.

23. **Remaining work.** Manual desktop/mobile/keyboard walkthrough; S-ORD-03 authorized segment transitions and event history; S-ORD-04 pickup/fulfillment integration; separately authorized future Buyer attribution work and financial evidence reconciliation. None of these workflows was introduced here. All changes remain local for review, with pre-existing untracked work retained.
